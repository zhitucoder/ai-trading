# 分红数据展示设计 —— 分红列表 · 个股画像分红栏 · 分红趋势 · 筛选

> 版本：v1.1 | 日期：2026年8月
> 关联代码：`src/app/routers/profile.py`、`src/app/strategies/dividend.py`、`scripts/fetch_dividend.py`、`web/index.html`、`web/app.js`、`web/style.css`
> 数据：`stock_dividend` 表（东财 RPT_SHAREBONUS_DET，全量 5121 只 / 54212 条）

## 一、背景与目标

分红数据已具备完整的数据层（`stock_dividend` 表 + 抓取脚本），但展示层只有两个零散入口：

1. 个股画像页一张"分红信息"卡片（字段平铺）
2. 画像筛选页一个"股息率 ≥/≤"输入框

用户希望分红成为**可浏览、可钻取、可筛选**的完整功能，具体需求：

- **分红列表**：独立页面，全市场分红一目了然（按报告期/除息日/股息率浏览）
- **列表 → 画像跳转**：点击任意分红记录进入该股个股画像
- **个股画像分红栏**：画像页有专门一栏展示分红数据 + **分红趋势图**（历年每股派息/股息率走势）
- **画像筛选支持分红**：筛选页提供完整的分红维度筛选（股息率、分红比例、今年是否分红、中期分红等）

### 1.1 设计原则

1. **复用既有数据层**：所有数据来自 `stock_dividend` 表，不新增抓取逻辑，不改表结构
2. **列表走独立接口，画像走 profile 返回**：列表用分页 SQL，画像页沿用 `/api/profile/{code}` 已返回的 `dividend` 字段（避免重复请求）
3. **趋势图前端绘制**：canvas 绘制，与现有财务趋势图（`fin-chart`）同一风格，无新依赖
4. **筛选字段落 `stock_profiles` 标量列**：保证 SQL 索引过滤，与现有 57 个标签列同构

- **进度反馈**：复用现有 `.dm-toast` 成功/失败提示 + spinner

### 7.2 增量更新原理

`stock_dividend` 表的 `updated_at`（`ON UPDATE CURRENT_TIMESTAMP`）记录每条记录的最近写入时间；全量抓取时使用 `ON DUPLICATE KEY UPDATE`，已存在记录自动刷新 `updated_at`。

**增量抓取逻辑（`scripts/fetch_dividend.py` 新增 `--since` 参数）：**

```bash
python scripts/fetch_dividend.py --since 2026-08-01 --workers 8
```

- `since` = 库内 `MAX(updated_at)` 对应的日期（首次全量抓取时用 `--since 2021-01-01`）
- 抓取时**不能只按日期过滤接口返回**（东财接口无"变更时间"参数），而是：
  1. 仍然拉取该股票全量分红列表（接口按 `REPORT_DATE` 排序，一次最多约 50 条，成本低）
  2. 写入走 `ON DUPLICATE KEY UPDATE`——**已存在的记录原地更新，新记录插入**
  3. 结果天然是"增量"语义：无论方案变化、实施进度推进（预披露→实施分配）还是新增分红，全部自动同步，无需增量判断逻辑
- **真正的"增量"体现在跳过已确认无变化的股票**：
  ```python
  # fetch_dividend.py 新增：只处理 since 之后有变化的股票
  # 方案A（简单，推荐）：全量拉取所有股票，靠 UPSERT 自动更新
  #     —— 每只 ~0.5s × 5121 只 ≈ 45 分钟，可后台跑
  # 方案B（省时）：仅拉取近 30 天除息日/公告日/报告期 ≥ since 的股票
  #     —— 接口 filter 加 (EX_DIVIDEND_DATE >= 'since' OR NOTICE_DATE >= 'since')
  #     —— 大幅减少请求量，秒级完成
  ```

> **推荐方案B**：东财接口支持 `filter` 多条件（`AND`），增量时给 filter 追加 `(EX_DIVIDEND_DATE >= 'since' OR PLAN_NOTICE_DATE >= 'since')`，只抓近期有分红动作的股票；再配合 UPSERT 覆盖。这样既快又不会漏。

## 九、风险与注意事项

1. **趋势图与财务趋势图并存**：画像页已有营收/净利趋势 canvas，分红趋势为独立 canvas，注意复用绘制函数避免重复代码
2. **`trend` 按除息日归属年份**：跨年分红（如 2025年报 2026年6月派息）归入派息年份，与"今年每股派息"口径一致，避免混淆
3. **`consecutive_dividend_years` 计算成本**：全量刷新时每只股票一次 `stock_dividend` 聚合，5000 只可接受；若变慢可预聚合到临时表
4. **中期分红识别**：依赖 `is_mid_year`（报告期为3/6/9月），已在抓取脚本处理
5. **手动数据一致**：列表/画像/筛选三入口同源 `stock_dividend`，不会出现三处口径不一致
6. **东财字段含义**：`PRETAX_BONUS_RMB` 是每10股派息，换算每股时除10；`DIVIDENT_RATIO` 是小数需×100 转百分数（抓取脚本已处理）
7. **增量更新语义**：`since` 只用于**缩小抓取范围**（方案B filter），真正的数据同步靠 `ON DUPLICATE KEY UPDATE` 幂等覆盖——已存在的行自动更新、新分红自动插入，无重复数据风险
8. **抓取耗时**：方案B 增量仅抓近期活跃股票，秒级到分钟级；`_update_lock` 防止与日K/财务更新并发冲突（共用同一把锁）
9. **接口频率限制**：东财接口无公开频控，但 8 并发全量抓取需留意被限流，`fetch_dividend.py` 已带重试（MAX_RETRIES=3）与线程池限流
