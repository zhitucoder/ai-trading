# 年报/半年报 PDF 解析与智能分析 —— 技术方案

> 版本：v1.0 | 日期：2026-09-06
> 关联：`src/download_reports.py`、`report_pdf` 表（1327 条）、`docs/年报管理层讨论与分析_MD&A数据利用_设计方案.md`、张新民分析流程
> 目标：把已下载的年报/半年报 PDF 变成「张新民分析 / 达摩达兰估值 / AI 蒸馏专家」等 Skill 的知识来源

## 一、先回答你的三个问题（结论先行）

| 方案 | 结论 | 一句话理由 |
|:---|:---|:---|
| **直接把 PDF 给 agent 读** | ❌ 不直接读 PDF | agent 读不了二进制 PDF，必须先用程序提取成文本/表格 |
| **DeepSeek OCR / 腾讯混元 OCR 解析** | ⚠️ **对当前库不需要**，仅作扫描件兜底 | 你的年报全是**文本层 PDF**，OCR 反而会引入识别误差、更慢更贵 |
| **LlamaIndex + 本地 1.8B/8B 私有化模型查文档** | ⚠️ **单公司分析不需要，全库问答才值得** | 1.8B/8B 做不了财务推理；本地模型只配做「索引/粗筛」，最终分析仍交给云端强模型 |

**核心结论一句话**：

> 你的库是**电子版文本 PDF**，正确路径 = **PyMuPDF 直接提取文本 + 表格还原**，按「提取层 → 知识层 → 消费层」三层架构接入 Skill。
> OCR 只在遇到**扫描版/图片型 PDF**时启用；本地小模型 RAG 只在「全市场 1300+ 份开放问答、隐私/离线」场景才值得投入。

## 三、三条路线的本质对比

> 关键认知：**「提取」和「理解」是两个问题，要分开选型。**
> - 提取（PDF → 文本/表格）：决定数据质量，坏解析 = 坏分析，后面接多强的模型都救不回来
> - 理解（文本 → 分析结论）：决定分析质量，强模型 >> 本地小模型

### 3.1 提取层：PyMuPDF vs OCR vs MinerU

| 维度 | PyMuPDF（规则提取） | DeepSeek-OCR / 腾讯云OCR | MinerU（VLM） |
|:---|:---|:---|:---|
| 适用 PDF | **文本层 PDF**（你的库 ✓） | 扫描版/图片型 PDF | 两者都行，侧重复杂表格 |
| 速度 | **50+ 页/秒**，无模型加载 | 0.2~2 页/秒，按页计费 | 0.3~2 页/秒，需 GPU（≥8GB） |
| 成本 | **0 元** | 每页计费（约 0.05~0.2 元/页） | 自部署免费（AGPL 协议注意商用） |
| 表格还原 | `find_tables()` 中等（财务表够用） | 好 | **最强**（表格 F1≈94.8%） |
| 对文本层 PDF 精度 | 100% 原文，无误差 | 反引入 OCR 错字风险 | 略降（多一道视觉转写） |
| 长文档（200+页） | 无限制 | token/页数限制多 | 支持分块 |

**决策规则**：

```
1. 检测：pymupdf 每页 get_text()，若整份 PDF 文本层完整 → 走 PyMuPDF
2. 若遇到扫描版（文本层 < 30%）→ 上 OCR：
   · 有 GPU → MinerU（开源，中文/财报最优，离线）
   · 无 GPU → 云端 OCR（腾讯云OCR / DeepSeek-OCR 3B 服务）
3. 复杂嵌套表格（合并单元格、跨页表）要求 100% 准 → MinerU 或商用（TextIn xParse）
4. 日常分析不需要步骤 3 —— 财务三表你的数据库里已有结构化数据（ads_*），年报表格主要看附注和分部数据
```

### 3.2 消费层：强模型直接读 vs 本地小模型

| 维度 | 云端强模型（deepseek-v4 / claude） | 本地 1.8B/8B |
|:---|:---|:---|
| 财务推理（六维分析/估值） | ✅ 强 | ❌ 明显不足，会「一本正经编数字」 |
| 成本 | 单公司一次约几毛钱 | 0（电费外） |
| 隐私 | 文本出域 | 完全本地 |
| 适合角色 | **分析者**（最终结论） | **索引器/粗筛器**（chunk、分类、打标签） |

**结论**：分析必须用强模型。1.8B/8B 可以跑在「提取→理解」之间做廉价流水线（如批量判断 MD&A 增长信号强弱、给 1300 份年报粗筛出值得深挖的 20 份），但**最终六维分析/估值结论永远交给强模型**。

### 3.3 是否用 LlamaIndex + RAG？

RAG 解决的是「**不知道查哪份文档**」的问题（全库检索）。你的场景分两种：

| 场景 | 需要 RAG 吗 | 正确做法 |
|:---|:---|:---|
| **单公司深挖**（张新民分析 XX） | ❌ 不需要 | 已知代码 → 直接取该 PDF 提取结果 → 喂强模型。RAG 检索反而可能召回错章节 |
| **全市场/行业问答**（哪家公司年报提到低空经济） | 可用 | 优先复用 `report_mda` 的 FULLTEXT 检索 + `sector_mda_ai` 聚合（见 MD&A 设计文档），**数据库检索 > 向量检索**（可精确、可追溯） |
| 极少数「任意自然语言模糊问答」 | 才需要 | 再考虑 embedding + bge-reranker，生成仍用强模型 |

> **本项目正确的 RAG 形态是「MySQL 结构化知识表」，不是「向量库」。** 与 `ads_*`、`report_mda` 同一套路：离线预计算好、在线秒查、可 SQL 追溯。

### 各层职责与红线

- **提取层只跑一次**，产出带页码锚点的中间产物；后续任何 Skill 不再碰 PDF
- **数据质量在提取层锁死**：表格必须还原结构（科目↔数值对应），坏表格会直接污染财务推理
- **消费层永远用强模型**，本地小模型最多做粗筛流水线
- 与 `ads_*` 一致：**结构化量化数据仍是权威主数据**，年报文本用于补充定性信息（管理层自述、行业判断、风险、附注、分部数据），两者交叉验证

## 五、核心代码（可直接落地）

### 5.1 文本层检测（决定要不要 OCR）

```python
import pymupdf  # aitrading 环境已装

def text_coverage(path: str) -> float:
    doc = pymupdf.open(path)
    low = sum(1 for p in doc if len(p.get_text().strip()) < 50)
    return 1 - low / doc.page_count

# 你的库实测 ≈ 0.99+ → 走文本提取；< 0.3 的才标记扫描件
```

### 5.2 章节定位 + 文本提取（复用 MD&A 方案逻辑）

```python
import pymupdf, re

def extract_sections(path: str):
    """定位「第三节 管理层讨论与分析」和「第八节 财务报告」，返回带页锚文本"""
    doc = pymupdf.open(path)
    # 1. 读目录页找章节起始页码
    toc_candidates = []
    for pno in range(2, min(6, doc.page_count)):
        for hit in re.finditer(r"(第[一二三四五六七八九十]+节|管理层讨论与分析|财务报告)", doc[pno].get_text()):
            toc_candidates.append((hit.group(1), pno))
    # 2. 从起始页顺序读，遇到下一个「第X节」停
    start = find_section_start(doc)      # 详见 src/extract_mda.py 同款逻辑
    mdna = collect_until(doc, start, stop_pattern=r"第四节\s*公司治理")
    # 3. 三表：定位「合并资产负债表/利润表/现金流量表」表格页，逐页 find_tables()
    tables = []
    for pno in financial_page_range(doc):
        for tab in doc[pno].find_tables():
            tables.append({"page": pno, "md": tab.to_markdown()})
    return {"mdna_text": mdna, "tables": tables}
```

> 提取细节（目录页退化逻辑、子节 `^[一二三四五六七八九十]+、` 拆分）已在 `docs/年报管理层讨论与分析_MD&A数据利用_设计方案.md` 第 3.1 节定义，直接复用。

## 六、本地 RAG（1.8B/8B）什么时候才值得做

| 触发条件 | 说明 |
|:---|:---|
| 全市场 1300+ 份开放模糊问答 | 「哪些公司年报提到'人形机器人'且今年扩产」这类，FULLTEXT/结构化表搞不定的模糊语义 |
| 隐私要求 | 报告文本不出内网 |
| 离线环境 | 无外网 / API 不可用 |

如果做，**正确姿势**（避免踩坑）：

```
1. 解析仍用 PyMuPDF/MinerU（本地小模型不碰 PDF，解析质量由提取层保证）
2. embedding 用 bge-large-zh-v1.5（检索） + bge-reranker-v2-m3（重排）
   不要用 1.8B 端到端问答，检索质量主要由 embedding 决定
3. chunk 按「章节边界」切（第三节MD&A/第八节三表），不要按 token 硬切 ——
   硬切会切断「第三节引用第八节表格」的跨章节关联（财报分析大忌）
4. 生成/分析仍调云端强模型；1.8B/8B 只做：
   · 批量粗筛（1300 份 → 值得深挖的 20 份）
   · 给 MD&A 打信号标签（policy/capacity/risk）喂给 stock_mda_ai 的预计算
```

**明确不做的事**：
- ❌ 用 1.8B/8B 直接做张新民六维/估值分析 —— 财务推理会「一本正经编数字」，且无法交叉勾稽
- ❌ 为单公司分析上 RAG —— 已知代码直接取提取结果即可，检索是多余的

## 九、风险与注意事项

1. **坏表格污染分析**：财务表科目↔数值对应必须还原；PyMuPDF `find_tables()` 对合并单元格/跨页表可能错位，三表建议优先用 `ads_*` 权威数据，年报表格只看附注/分部/管理层口径
2. **管理层自述有宣传成分**：MD&A 偏乐观，只作线索与引用，不作为结论（与 MD&A 设计方案一致）
3. **跨章节引用断裂**：chunking 必须按章节边界，否则「第三节引用第八节表格」会断
4. **扫描件兜底**：个别老报告/签名页是图，用 `text_quality` 标记，走 MinerU/OCR 补，不要全局 OCR
5. **可追溯性**：所有引用保留页码锚点（`page_map`），避免 LLM 编页码
6. **token 预算**：单份年报全文 ~10 万字符，直接全喂超预算；喂 `mdna_text + tables_json`（~1.5万字符）足够六维分析，全文仅按需检索
7. **AGPL 许可证**：MinerU 商用需开源同协议；本项目学习研究无碍，若商用选商业解析 API 或换协议兼容工具

## 十、附：一句话给每个方案定性

- **直接读 PDF**：方向对（最终消费模型直接读文本），但 agent 读的是**提取后的文本**，不是二进制 PDF
- **OCR**：对你现有文本层库 = 画蛇添足；留给扫描件
- **本地小模型 RAG**：是「索引器」不是「分析器」；本项目主场景用不着，先做结构化知识表

> 与本项目 `ads_*` 哲学一致：**离线预计算、在线秒查、SQL 可追溯**。年报文本按同一套路沉淀为可查询知识，而不是每次现场翻 PDF。
